### Конкретные препятствия в коде

1. `server/security.mjs` открывает файл `owner.sqlite` через `DatabaseSync` и хранит ключ на файловой системе. `server/accounts.mjs` и `server/app.mjs` рассчитывают на синхронные операции и `BEGIN IMMEDIATE/COMMIT/ROLLBACK`. D1 не является заменой одной строки импорта: нужно переработать адаптер и атомарность операций.
2. Параметры scrypt: N=131072, r=8, p=1; `maxmem=192*1024*1024`. Оценка основного буфера `128*N*r` составляет 128 MiB ещё до накладных расходов. У Worker 128 MB на весь isolate. Это анализ кода и лимитов, а не результат нагрузочного теста в Workers. Уменьшение стойкости хеширования не выполнено.
3. `npm run admin:setup` — интерактивная серверная CLI-команда. Для Workers потребуется новый доверенный механизм первичного назначения владельца, не «первый зарегистрировавшийся» и не email/роль из клиента.
4. Клиент использует same-origin `/api/account`; админка — `/api/admin`; социальный вход — `/auth/*`. Простая публикация папки `dist` не сохранит эти функции.
5. Социальный вход требует секретов приложений владельца. Реальные Google/Meta аккаунты в этой работе не использовались.
6. В текущей среде managed Sites нет пользовательского локального предпросмотра. Документированные managed-preview возможности предназначены для внутренней QA; browser skill здесь недоступен. Native Sites deployment URL является production URL даже при owner-only доступе. Поэтому запрет публикации соблюдён, отдельный работающий preview не заявлен.

## Варианты адаптации до изменения поведения

### A. Сохранить Node.js-сервер отдельно — рекомендуемый вариант для сохранения текущего входа

Сохранить имеющиеся SQLite, scrypt, email/пароль, OAuth, TOTP и административные проверки на сервере Node.js 22.16+ с постоянным приватным диском. Sites может обслуживать интерфейс и серверный шлюз к этому backend по HTTPS.

Перед реализацией нужны адрес backend и решение о месте его запуска. Доступ и секреты вводятся через поддерживаемую защищённую конфигурацию, не в чат и не в GitHub.

Адаптация должна:
- сохранить same-origin маршруты для клиента;
- строго разделить внешний origin Sites и внутренний адрес backend, корректно проверять Host/Origin, CSRF, cookie, redirects и OAuth callback;
- защитить соединение шлюз → backend и не доверять произвольным forwarded-заголовкам;
- сохранить отдельные проверки роли владельца;
- отдельно решить встраивание и проверить вход в верхнем окне.

Это гибридный перенос: сервер останется вне Sites. Он не развёрнут в этой работе.

### B. Полностью перенести сервер в Workers/D1

Сохранить существующий интерфейс, перенести API на Workers, схему и запросы — на D1, ключи — в серверные секреты. Требуются асинхронные запросы, миграции, конкурентно безопасные ограничения попыток и операции выдачи/отзыва сеансов.

Встроенный вход ChatGPT меняет существующий способ регистрации и управления паролем. Такой переход требует отдельного решения владельца. Если email/пароль должен сохраниться, нужна подтверждённо поддерживаемая внешняя служба авторизации или сохранение текущей Node.js-службы; бесшумная замена/ослабление scrypt недопустима.

Права владельца должны назначаться доверенно на сервере; сопоставление существующих аккаунтов по неподтверждённому email недопустимо.

После этого отчёта владелец выбрал подготовку отдельного запуска: добавлен автономный Node.js-комплект, описанный ниже. Подключение backend к Sites ещё не выполнено.

## Дополнение: отдельный запуск, 17 октября 2026

По просьбе владельца подготовлен запуск существующего Node.js backend без аренды сервера и публикации:

- `start-standalone.bat` / `start-standalone.sh`: готовая сборка запускается на компьютере владельца, без npm при наличии dist; первый запуск вызывает существующую интерактивную настройку владельца.
- `server/standalone.mjs`: проверка уже существующего владельца без создания/замены базы, проверка папки данных до настройки, запуск только на loopback в обычном режиме, корректное завершение сервера.
- `Dockerfile`, `compose.yaml`: дополнительная контейнерная поставка, loopback-порт хоста, отдельный постоянный том SQLite/ключа, непривилегированный процесс и healthcheck.
- `tests/standalone.test.mjs`: отдельные регрессионные проверки первого запуска и отказа при потере ключа, реального HTTP-входа, сохранения проекта, прав владельца и перезапуска готовой поставки.
- `STANDALONE-START.md`: инструкция для Windows, macOS/Linux и Docker.

Исходные 80 файлов приложения остались неизменны. Новые файлы запуска используют существующие createApp/setup/security; парольная авторизация и серверные проверки сохранены. Docker-движок в текущей среде отсутствует: конфигурация подготовлена, но образ и том в Docker здесь не запускались. Windows/macOS отдельно не проверялись.

Следующий шаг после получения HTTPS backend — защищённое соединение Sites с этим сервером. Локальный localhost не доступен из Sites. Запрет публикации и подключения домена остаётся в силе.
