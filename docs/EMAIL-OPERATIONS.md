# Service email for Pokadrovo

Vite includes the pinned mail library and its license in the private `dist/server` runtime so verified VPS and standalone deliveries do not require runtime npm installation. The static server denies HTTP access to that directory. Development may use the installed npm dependency if the bundle is absent.

The integration is implemented; this does **not** mean a RuSender account, SMTP connection or mailbox has been created. Production defaults to disabled. Never enable with invented sender credentials, claim receipt from a queued/SMTP-accepted state, buy a plan, attach a card or bypass provider/domain activation. The only domain in scope is **pokadrovo.ru**.

## Free setup

1. The operator creates their own RuSender account at https://app.rusender.ru/auth/register, chooses **Free API+SMTP**, and personally completes credential entry and contractual acceptance. No card or paid plan is needed for the free trial workflow. Confirm the provider's current terms and quota; the generic marketing Free quota is a different product.
2. In RuSender, configure the owned domain and sender, for example `noreply@pokadrovo.ru`. Add only the exact DNS records returned for that domain. Preserve the existing website A/AAAA records and nameservers. Never publish a guessed DKIM key or create a second conflicting SPF record. Sender-address availability/verification is a separate provider prerequisite, not proof an inbox was created.
3. Create the SMTP connection, complete the provider's activation, and obtain its SMTP login/password. Current documented transport is **smtp.rusender.ru, port 465, TLS/SSL**. SMTP host/port are deliberately fixed in this implementation; arbitrary destinations, URL/file message access, debug logs and insecure TLS are not accepted.
4. Review the actual processor role, identity, processing country, terms and notices; enter the real facts in Documents and details and review/publish the current document edition. Public user mail requires both enabled SMTP configuration and current published legal readiness. These controls are not a legal-compliance guarantee.
5. In **Почта сайта**, enter the sender and both SMTP credentials, confirm the no-charge plan/domain/processing checks, enable and submit with current owner-password reauthentication. The server encrypts both SMTP values using its existing private master key and returns only configured flags. Blank inputs preserve them; changes require both credentials. Removing credentials disables delivery. No financial-provider settings are changed.
6. Explicitly send **one** test to the operator's own chosen address (up to three owner tests/hour), refresh status and inspect the real inbox and spam folder. A test uses the same quota. SMTP acceptance is not proof of inbox delivery. Test credentials are never test emails and are never written into Git or chat.

References checked: https://rusender.ru/pricing/ and https://rusender.ru/knowledge-base/email-service/email-api/kak-nachat-rabotu-s-smtp/ . Provider changes require a new review. No support message has been sent on the operator's behalf by this implementation.

## No-charge bounds and delivery state

The hard application cap is **100 reserved messages per rolling 32 days**. It is deliberately more conservative than the provider's 100/month Free API+SMTP allowance. Every queued reservation, explicit test, failed/cancelled or uncertain attempt counts until it ages out; there are no automatic purchases, excess-quota charges initiated by the app or automatic retries. Use a dedicated unused SMTP connection/account so unrelated sends do not consume the same external quota. This app cannot control provider settings changed outside it.

The SQLite reservation is atomic and survives restarts; queued plaintext is never retained. Pending payloads (recipient, proof link) are encrypted, then cleared before attempting SMTP, on cancellation or expiry. A single sequential worker runs while the server listens. A saved configuration change cancels old pending jobs. A worker restart marks `sending` as interrupted and does not retry an uncertain SMTP operation. SMTP errors are replaced by fixed operator guidance, not raw errors containing credentials/recipient information. The log retains only kind, dates, generic status/error and revision. Completed history is cleaned after 33 days. After restoring an older database, keep mail disabled until the local reservation history is reconciled with actual provider usage; an old snapshot is not a new provider quota. A normal server restart cannot replenish the quota; local DB backups retain older snapshots under the existing private rotation policy.

## Verification and reset

- If delivery is ready, signup queues one verification mail; signup itself does not prove email ownership. The user still receives the existing one-time offline code. Existing accounts are not silently verified.
- Profile → Профиль allows resend, at most once/minute and three account sends/day. Delivery depends on quota and provider acceptance. Repeated verification supersedes the previous proof.
- Confirmation links require an explicit POST and login to the same normal account for which the proof was issued. A browser prefetch, mail scanner or forwarded link cannot silently mark another account verified. If signed out, sign in then reopen the original email link.
- Forgot password offers email when configured and retains the offline-code alternative. Reset requests always use the same response for unknown, disabled and unverified addresses; mail is queued only for an active password account with a verified address. An unverified user must first verify while signed in or use their offline code. Support must not mark ownership based on a claimed email alone.
- Link proofs contain 256 random bits; only keyed digests are stored in the token table. They are bound to user, kind, current email/password and active status. Verification expires after 24 hours, reset after 30 minutes. New proof, password change, expiry or successful consumption invalidates old proof. Concurrent reset consumes at most once.
- URLs use `#verify=...` / `#reset=...` fragments on the canonical origin's `/account/email` page. HTTP requests do not carry the fragment. That isolated page has no analytics/third-party assets, is noindex/no-referrer/no-store, immediately removes the fragment from history and keeps proof only in memory. Reloading the empty action page requires reopening the original email. A user-selected copy action can put the new offline code on their clipboard.
- Reset never automatically signs in; it revokes all previous user sessions, rotates and shows a fresh offline code once, and preserves projects, wallet and document receipts. It cannot reset owner credentials or TOTP. No password or offline recovery code is emailed.
- Consuming an already delivered valid proof and offline-code recovery remain possible if new sending or registration is paused. New user mail waits for real legal readiness; existing login and guest editing are retained.

## Validation and limits

Isolated HTTP/SQLite tests use an injected fake transport and synthetic addresses: no real email or paid provider request. Checks cover owner isolation/reauth/CSRF/origin, encrypted configuration and queue, fixed TLS transport, unknown/unverified reset responses, proof expiry/reuse/rotation, wrong-account verification, racing reset, session revocation, preserved data, conservative persisted quota and redacted failures without retry. Production smoke checks can prove code/state/UI availability; only an explicit real inbox test after genuine setup proves that delivery works.
